# postgres-csv-clean

The agent writes `/app/clean.sh`, a psql script that: creates a `customers`
table, imports the raw `/app/data/customers.csv` (no header) via client-side
`\COPY`, cleans the data *inside* PostgreSQL (dedupe by non-id fields keeping the
lowest id; delete rows missing both email and phone; strip non-digits from phone;
lowercase email), and exports `/app/data/cleaned_customers.csv` (header, ordered
by id) via client-side `\COPY`. The verifier starts its own PostgreSQL, runs the
agent's `clean.sh` against it, and grades the resulting database and CSV.

## Why this scenario discriminates

14 pytest cells split CSV correctness, database state, and proof-of-postgres:

- **CSV cells (8):** existence, exact header, per-column presence, no duplicate
  (name,email,phone,city) tuples, email lowercase + at-least-one-of-email/phone,
  digits-only phone, exact row-equality against the hidden baseline
  `customers_v1.csv`, and id-ascending ordering.
- **Database cells (4):** the `customers` table exists with the exact 5-column
  typed structure; the table contents are semantically equal to the exported CSV
  *and* to the baseline. A solution that produces a correct CSV without populating
  postgres (or that hardcodes the 17 expected rows) fails these outright.
- **Proof-of-postgres (2):** `pg_stat_statements` must show the cleaning
  `UPDATE ... regexp_replace(...)` / `UPDATE ... lower(...)` / `DELETE ... USING`
  statements AND client-side `\COPY` (recorded server-side as `COPY ... FROM
  STDIN` and `COPY ... TO STDOUT`); `test_psql_commands_were_used` is a soft
  upstream check (see below).

Null floor is **1/14** (verified): with an empty/broken `clean.sh`, only
`test_psql_commands_were_used` passes — it falls back to detecting the verifier's
own running postgres process, so it passes regardless of the agent and is a
constant, not a discriminator (same accepted shape as query-optimize's constant
fixture-sanity floor). The pandas/sed cheat scores **9/14** (verified — all 8 CSV
cells + the constant), losing exactly the 4 database cells + the
pg_stat_statements cell.

## The reshape (why this port is high-risk)

Upstream ran a 2-service docker-compose: an app `client` and a separate
`postgres:16` `db` service started with
`-c shared_preload_libraries=pg_stat_statements -c log_statement=all`. The agent
connected at `db:5432` and the tests inspected *that* server's
`pg_stat_statements`. trajrl-bench has no compose and a hard agent<->verifier
container split, and postgres/pg_stat_statements state does not cross it. If the
agent cleaned against a postgres in the *agent* container, the verifier could
never see the evidence and every miner would fail 5 cells.

Resolution, encoded here:

1. **One image.** postgres + postgres-contrib are installed in the scenario
   image; a shared `pg-up.sh` (baked at `/usr/local/bin/pg-up.sh`) brings up a
   fresh cluster with `pg_stat_statements` preloaded, `log_statement=all`, and
   `pg_stat_statements.track=all`/`track_utility=on`. The agent and the verifier
   use the *same* script, so the DB the agent develops against is byte-for-byte
   the one that scores. (Debian ships postgres **17**; the bring-up globs
   `/usr/lib/postgresql/*/bin` so it is version-agnostic.)
2. **Deliverable = `/app/clean.sh`.** `agent_output_path` names that single file
   (not a directory — `_extract_file` returns None for a directory's first tar
   member). The verifier extracts it into a fresh container, starts postgres,
   runs `clean.sh` against it, then runs pytest — so the pg_stat_statements
   evidence is generated by the *verifier's own* session.
3. **Non-root postgres.** The server refuses to run as root; the verifier's
   `test.sh` runs as root and invokes `su postgres -c 'bash /usr/local/bin/pg-up.sh'`,
   while the agent (hermes) runs the same script directly. `pg-up.sh` hard-refuses
   EUID 0.
4. **Localhost repoint.** The 5 `psycopg2.connect(host="db", ...)` calls are
   repointed to `host=os.getenv("PGHOST", "127.0.0.1")`, since postgres now runs
   in the same container. `initdb -A trust -U postgres` makes 127.0.0.1
   connections trusted (the tests' `password="postgres"` is accepted-and-ignored)
   and fixes the superuser role name to `postgres`.
5. **Pinned input, hidden baseline.** Only `clean.sh` crosses the boundary, so
   the verifier's `/app/data/customers.csv` is the pristine image copy;
   `test.sh` additionally re-copies it from the verifier-only `/tests/customers.csv`
   before running `clean.sh`. `customers_v1.csv` is never baked into the
   agent-visible image and is dropped into `/app/data` only *after* `clean.sh`
   runs, so a `cp customers_v1.csv cleaned_customers.csv` shortcut is impossible.

### Modifications during adaptation

- **`environment/Dockerfile`** FROMs `sandbox-agent` (vs. upstream
  `t-bench/ubuntu-24-04`) and installs `postgresql postgresql-contrib`; drops
  upstream's build-time `CREATE USER root` / `createdb` dance (a fresh cluster is
  initialized at grade time by `pg-up.sh` instead); bakes the raw `customers.csv`
  into `/app/data` and the shared `pg-up.sh` into `/usr/local/bin`; installs
  pandas + psycopg2-binary for agent convenience only (the verifier imports
  neither via the image — psycopg2 comes in via uvx, pandas is unused by tests).
- **`environment/pg-up.sh`** is new (no upstream equivalent — upstream got its
  configured server from the compose `db` service and `init/001_*.sql`). It folds
  the compose `db` service's config (`shared_preload_libraries`, `log_statement`)
  and the init SQL (`CREATE EXTENSION pg_stat_statements`) into one script usable
  by both the agent and the verifier as a non-root user.
- **DB encoding fix (not in the original draft).** `initdb -A trust` in this
  image's C locale defaults the cluster to **SQL_ASCII**; psycopg2 then decodes
  the non-ASCII names/cities (e.g. UTF-8 `0xc3` lead bytes) with the ascii codec
  and `cur.fetchall()` raises `UnicodeDecodeError`, failing
  `test_postgres_data_consistency` and `test_postgres_matches_customers_v1_csv`
  (the `\COPY` CSV export is unaffected — it writes raw bytes). `pg-up.sh`
  therefore creates `customers_db` as `--encoding=UTF8 --template=template0
  --lc-collate=C --lc-ctype=C` (C locale is encoding-agnostic in postgres), which
  fixes both cells; verified `SHOW server_encoding` = UTF8 and reference 14/14.
- **psycopg2-binary pinned to 2.9.10 (not upstream run-tests.sh's 2.9.9).** The
  base image ships Python 3.13, for which psycopg2-binary 2.9.9 has no wheel (pip
  falls back to a source build and fails); 2.9.10 is the first release with cp313
  wheels. Bumped in both the Dockerfile bake and the `tests/test.sh` uvx line.
- **`tests/test_outputs.py`** upstream verbatim except: canary removed; `import os`
  added; the 5 `psycopg2.connect(host="db", ...)` calls repointed to
  `host=os.getenv("PGHOST", "127.0.0.1")`. `test_psql_commands_were_used` is kept
  as-is though it degenerates to a constant pass in this reshape (documented above).
- **`tests/test.sh`** brings up postgres via `su postgres -c pg-up.sh`, re-pins
  the input from `/tests/customers.csv`, runs the agent's `/app/clean.sh`, drops
  the baseline `customers_v1.csv` in *after* that, then runs the 14-cell ctrf
  pytest with `psycopg2-binary==2.9.10` (via uvx).
- **`tests/customers_v1.csv`** the exact upstream baseline, kept only under
  `tests/` (verifier-only) so the agent cannot copy it.
- **`solution/solve.sh`** writes `/app/clean.sh` = upstream `solution.sh`'s
  create/`\COPY`/clean/`\COPY`-out sequence, canary removed and `DB_HOST`
  repointed from the compose `db` service to `127.0.0.1`.
- **`instruction.md`** upstream `task.yaml` instruction, retargeted to
  `127.0.0.1` and the `/app/clean.sh` deliverable.
- No copyleft is bundled: postgresql/-contrib are apt system packages; pandas is a
  BSD pip package; the 821 B CSVs are the task's own fixture data.

## Deliverable

`agent_output_path = /app/clean.sh`. The validator extracts it from the agent
container and injects it into a fresh verifier container of the same image;
`tests/test.sh` starts postgres, runs `clean.sh` against it so the cleaning +
`\COPY` queries populate the verifier's own `pg_stat_statements`, places the
hidden baseline, then runs the 14-cell pytest suite.

## Verification

The port sign-off produces `clean.sh` in an agent container (as hermes), extracts
*only* that file, injects it into a fresh verifier container, and grades there —
never `solve.sh && test.sh` in one container. Results (under the validator's real
2-CPU / 4-GB eval-sandbox model):

- **Reference: 14/14.** After the UTF8 encoding fix; `SHOW server_encoding` = UTF8.
- **pandas/sed cheat: 9/14** — loses exactly `test_postgres_database_connection`,
  `test_postgres_table_structure`, `test_postgres_data_consistency`,
  `test_pg_stat_statements_shows_cleaning_and_copy_queries`, and
  `test_postgres_matches_customers_v1_csv` (all 8 CSV cells + the constant pass).
- **Null floor: 1/14** — only the constant `test_psql_commands_were_used`.
- **pg_stat_statements evidence confirmed present** after the reference run:
  `COPY customers(...) FROM STDIN`, `COPY (SELECT ... ORDER BY id) TO STDOUT`,
  both cleaning `UPDATE`s, and the `DELETE ... USING` are all recorded (the
  single make-or-break assumption of the port — validated, not assumed).
